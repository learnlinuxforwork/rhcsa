Lab guide 12

Mock Exam, Remediation, and Exam Day

Find out whether you are actually ready, fix what the mock exposes, and walk into the real exam having already sat it once.

6-8 hours across the week Weeks 1-11 complete
Before you start
  • Weeks 1-11 complete
  • Both lab machines rolled back to a clean snapshot
  • Take a snapshot of both machines. You will break things on purpose.

1. Set the conditions honestly

A mock you cheat on tells you nothing. Reproduce the real constraints exactly.

Before you start the timer
# 1. Roll both machines back to the 'clean' snapshot
# 2. Close every browser tab except a clock
# 3. No notes, no lab guides, no search engine
# 4. Allowed: man, info, /usr/share/doc - nothing else
# 5. Set a timer. Do not pause it for any reason.

2. A self-built mock

Work these from a cold machine, in any order, in under three hours. They are written the way exam tasks are written - the outcome is specified, the method is not.

Users, groups, and access
# 1. Create user 'auditor' with UID 3200 and a shell of /bin/bash.
# 2. Create group 'audit' with GID 3300; make auditor a supplementary member.
# 3. auditor's password must expire every 30 days with a 5-day warning.
# 4. Members of 'audit' may run any command with sudo.
Storage
# 5. Create a 1 GiB partition on the spare disk, format it XFS,
#    and mount it permanently at /data/reports using its UUID.
# 6. Create a volume group 'appvg' and a 400 MiB logical volume 'applv'.
# 7. Format applv ext4, mount it at /data/app, then grow it to 700 MiB
#    without losing its contents.
# 8. Add 512 MiB of swap that activates automatically at boot.
Services, networking, and security
# 9.  Install and enable httpd. Serve content from /srv/reports
#     instead of the default location. It must work with SELinux enforcing.
# 10. httpd must listen on port 8404 and be reachable through the firewall.
# 11. Set a static IPv4 address that survives a reboot.
# 12. Configure key-based SSH from servera to serverb for user shea.
Automation and recovery
# 13. Write /usr/local/bin/diskcheck.sh that takes a mount point as $1,
#     prints its usage percentage, and exits 2 if usage exceeds 80 percent.
# 14. Run that script every 15 minutes via a systemd timer.
# 15. Make the journal persistent across reboots.
# 16. Set the system to boot into multi-user.target by default.
Then, and only then
sudo reboot
# When it comes back, re-check every single task.
# Score only what survived. Anything that needed a manual fix scores zero.

3. Score and remediate

The score matters far less than the list it produces.

Turn failures into a study plan
# For every task you missed or had to look up:
#   - Which objective domain does it belong to?
#   - Rebuild that lab from scratch, untimed, from the Week guide.
#   - Then do it again from memory, timed.
# Anything in the security or storage domains gets double attention -
# they carry the most weight and the most partial-failure risk.

4. The second mock

Later in the week, on a clean snapshot again.

Use a source you have not seen
# Sit a timed, hands-on mock you did not write yourself, so you
# cannot unconsciously remember the answers:
#   https://linuxcert.guru/
# Same rules: clean machines, timer running, man pages only, reboot at the end.

5. Book it

While the second mock is still fresh
# Book EX200 within two weeks of a clean mock pass:
#   https://www.redhat.com/en/services/training/ex200-red-hat-certified-system-administrator-rhcsa-exam
# Check your ID matches your Red Hat account name exactly.
# Test your machine against the proctoring requirements the day before.

Verify your work

Run these before you consider the lab finished.

  1. Every mock task re-checked AFTER a reboot
  2. A written list of every objective you had to look up
  3. A second timed mock passed cleanly
  4. Exam booked, ID checked, environment tested
Break it, then fix it

Break:

Skip the reboot at the end of the mock.

What you'll see: You score yourself 15/16 and feel ready. On the real exam you score far lower, because several configurations never persisted.

Fix:

Always reboot before scoring. Always.

Why it matters: This is the whole course in one sentence: the exam grades the state of the machine after a reboot, not the commands you typed. If you have internalised that by now, you are in good shape.

Now reboot

Run sudo reboot, then re-run every command in the verify list above. Anything that did not come back on its own would have scored zero on the exam. Fix it now, while you can still see what you did.
