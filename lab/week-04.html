Lab guide 4

Processes, Tuning, and Scheduled Tasks

Find and control running processes, adjust their priority, manage tuned profiles, and schedule work three different ways.

2-3 hours Week 3 complete
Before you start
  • Week 3 complete
  • Take a snapshot of both machines. You will break things on purpose.

1. See what is running

Learn one process listing well rather than three badly.

Snapshot and live views
ps aux | head
ps -ef --forest | head -20
top -b -n 1 | head -15
uptime
Sort by what actually matters
ps aux --sort=-%cpu | head -6
ps aux --sort=-%mem | head -6

2. Create load, then kill it

Make a process you can safely identify and terminate.

Start something noisy in the background
sha256sum /dev/zero &
sleep 300 &
jobs
ps -ef | grep -E 'sha256sum|sleep' | grep -v grep
Terminate it politely, then forcefully
pkill sha256sum
pgrep -a sleep
kill %2 2>/dev/null || pkill sleep
ps -ef | grep -c sleep
Signals worth knowing
kill -l | head -3
# SIGTERM (15) asks a process to exit; SIGKILL (9) cannot be caught or ignored

3. Scheduling priority

Lower nice values mean higher priority. Only root can lower a value below zero.

Start a process at a specific niceness
nice -n 10 sha256sum /dev/zero &
ps -o pid,ni,comm -C sha256sum
Change it while running
sudo renice -n -5 -p $(pgrep -n sha256sum)
ps -o pid,ni,comm -C sha256sum
pkill sha256sum

4. Tuning profiles

Named directly in the objectives, and quick marks if you know the three commands.

List, check, and switch
sudo dnf install -y tuned
sudo systemctl enable --now tuned
tuned-adm list
tuned-adm active
sudo tuned-adm profile throughput-performance
tuned-adm active
Let tuned choose for the hardware
sudo tuned-adm recommend
sudo tuned-adm profile $(sudo tuned-adm recommend)
tuned-adm active

5. One-off jobs with at

Schedule and inspect
sudo dnf install -y at
sudo systemctl enable --now atd
echo 'date >> /tmp/at-test.log' | at now + 1 minute
atq
at -c $(atq | awk '{print $1}' | head -1) | tail -5
Wait, then confirm it ran
sleep 70
cat /tmp/at-test.log
atq

6. Recurring jobs with cron

Both a user crontab and a system-wide job, because the exam may ask for either.

A user crontab
crontab -l 2>/dev/null
(crontab -l 2>/dev/null; echo '*/2 * * * * /usr/bin/date >> /home/shea/cron-test.log') | crontab -
crontab -l
A system-wide job that runs as a specific user
sudo tee /etc/cron.d/lab-report >/dev/null <<'EOF'
*/5 * * * * shea /usr/bin/uptime >> /tmp/uptime-report.log
EOF
sudo systemctl status crond --no-pager | head -5

7. systemd timers

A timer needs two units: the service that does the work, and the timer that triggers it.

The service unit
sudo tee /etc/systemd/system/labreport.service >/dev/null <<'EOF'
[Unit]
Description=Write a short system report

[Service]
Type=oneshot
ExecStart=/bin/bash -c '/usr/bin/date; /usr/bin/uptime' 
EOF
The timer unit
sudo tee /etc/systemd/system/labreport.timer >/dev/null <<'EOF'
[Unit]
Description=Run labreport every 10 minutes

[Timer]
OnBootSec=2min
OnUnitActiveSec=10min
Unit=labreport.service

[Install]
WantedBy=timers.target
EOF
Enable and inspect
sudo systemctl daemon-reload
sudo systemctl enable --now labreport.timer
systemctl list-timers --all | grep labreport
sudo systemctl start labreport.service
sudo journalctl -u labreport.service --no-pager | tail -5
Worth knowing

Reach for a timer over cron when you need the job tied to boot, dependent on another unit, or logged in the journal. Cron is still fine for simple recurring work.

Verify your work

Run these before you consider the lab finished.

  1. tuned-adm active
  2. crontab -l
  3. systemctl list-timers --all | grep labreport
  4. systemctl is-enabled labreport.timer # expect: enabled
Break it, then fix it

Break:

sudo sed -i 's/OnUnitActiveSec=10min/OnUnitActiveSec=nonsense/' /etc/systemd/system/labreport.timer && sudo systemctl daemon-reload

What you'll see: The timer refuses to start and systemctl reports the unit as failed or not loaded.

Fix:

sudo sed -i 's/OnUnitActiveSec=nonsense/OnUnitActiveSec=10min/' /etc/systemd/system/labreport.timer && sudo systemctl daemon-reload && sudo systemctl restart labreport.timer

Why it matters: systemd will not guess what you meant. 'systemctl status' plus 'journalctl -xe' names the bad directive and the line number. Always run daemon-reload after editing a unit file - forgetting it is the single most common systemd mistake.

Now reboot

Run sudo reboot, then re-run every command in the verify list above. Anything that did not come back on its own would have scored zero on the exam. Fix it now, while you can still see what you did.
